# MuWeave 项目管理改进方案

## 结论

推荐采用**轻量项目注册表 + `.muweave` 现有 `projectId` 聚合**。

- 项目身份、标题、项目级状态、封面安全引用、创建/更新时间、归档标记和 owner 绑定关系落在 DSH 的 `pluginDataDir/projects.v1.json`。
- 元件、场次、镜头、owner revision、状态和内容继续从对应 workspace 的 `.muweave/index.v1.json`、`bundle.v1.json` 及 owner CLI 读取。
- 注册表把 `projectId` 作为稳定连接键，但不复制元件、payload、owner 私有数据库或宿主绝对路径。
- 项目状态是用户对作品生命周期的判断，元件状态是单个信息元件的工作状态，两者并存，界面上分层展示。

每周只使用两小时的人可以只创建项目、绑定已有工作区、切换项目和查看下一步，不需要维护第二套内容库。项目注册表只记录少量项目元数据，`.muweave/` 损坏或删除后仍可通过 bundle sync 重建内容投影。

## 问题诊断

当前困惑集中在实际可见的几个位置。

1. **Workbench 右侧“原件与 Pi 动态”面板**把 Eikona 候选组、Auctra 场次、Scaena 分镜摘要和 Pi 工件放在同一条列表中。每行只有元件标题、来源和状态胶囊，列表顶部没有“当前项目”或项目切换器。用户无法判断两条同名场次是否来自同一作品，也无法回答“我有几个项目”。
2. **右侧面板的筛选区**目前只能按 domain、kind、owner、场次、角色或关键词筛选。筛选改变了列表内容，却没有改变信息归属。用户仍然看不到项目边界，也无法知道某条元件是项目内全部内容还是一次临时过滤。
3. **Workbench 的绑定与同步入口**只有 bundle bind/sync 语义。入口没有新建项目、复制项目、归档项目或切换项目的操作顺序。用户面对 owner 绑定时不知道应该先建项目，还是直接绑定 Eikona/Auctra/Scaena。
4. **排期房间**显示全局待排池和月历。排期条目只有 `ref`、标题、类型和日期，缺少项目上下文。用户在两个作品之间切换时无法确认当前 chip 属于哪一个作品，也没有项目级待发布视图。
5. **状态胶囊**把“元件就绪/待审阅/草稿”和用户希望看到的“项目筹备/制作中/待发布/已发布/归档”放在同一视觉层级。用户容易把一个元件的就绪误读成整部作品已就绪，或者以为项目状态会自动覆盖每个元件状态。
6. **项目目录与 owner 目录的关系**没有可见解释。`.muweave/` 是可重建物化包，`.eikona/.auctra/.scaena` 才是事实源。若把项目直接做成一套复制目录，用户会以为移动或复制项目就会复制全部事实，后续同步会产生分叉。

## 候选方案

### 方案 A：项目等于文件夹映射

**数据落点**

- 每个项目对应一个已注册 workspace 目录。
- 项目标题和项目状态从目录名、bundle manifest 或额外的同目录配置推导。
- owner 绑定继续写入该 workspace 的 `.muweave/bundle.v1.json`。

**优点**

- 用户直觉简单，复制文件夹即可看到一个“项目”。
- 迁移早期工作区的成本较低。
- 与现有 `workspace.register` 和 `bundle.status` 接口接近。

**缺点**

- 一个项目若跨多个 workspace 或多个 owner 根目录，边界无法表达。
- 标题、状态、归档和封面没有合适的持久落点，容易再次写进 `.muweave/`。
- 目录移动、重命名或备份还原会改变项目身份。
- 文件夹复制很容易被误认为复制了 owner 真相，实际只复制了物化投影。

**迁移成本**

- 低到中。可以把现有每个已初始化 bundle 目录映射为一个项目。
- 后续增加多 workspace 绑定时需要重新定义身份和引用。

**两小时每周负担**

- 单人单作品时负担低。
- 一旦同时维护两个作品、一个作品有多个 owner workspace，用户需要手动记目录和同步关系，负担会快速上升。

### 方案 B：项目等于 bundle 内 `projectId` 的聚合

**数据落点**

- `bundle.v1.json.projectId` 和 `index.v1.json.projectId` 作为项目连接键。
- 项目列表从已注册 workspace 的 bundle manifest 聚合生成。
- 项目标题主要来自 manifest，项目状态按元件状态和 owner readiness 推导。
- 若需要用户编辑的标题、归档和封面，必须另找持久化位置。

**优点**

- 复用已有字段，历史 bundle 可以直接读出项目身份。
- 元件查询天然按 `projectId` 聚合，`bundle.elements.list` 的返回结构容易延伸。
- bundle 删除后可通过 owner CLI 重建，不需要额外内容库。

**缺点**

- 仅靠派生数据无法可靠保存项目状态、归档意图和封面选择。
- 多个 workspace 使用同一 `projectId` 时，来源优先级和冲突处理不清楚。
- 项目复制、归档和绑定需要写入 bundle，容易把用户管理数据塞进可重建包。

**迁移成本**

- 中。需要补充旧 bundle 的聚合索引和冲突提示。
- 若后来再引入注册表，已使用的派生规则仍需兼容。

**两小时每周负担**

- 内容很少时几乎没有负担。
- 项目状态依赖推导规则，用户要花时间理解为什么项目状态变化，无法快速表达“内容没变但我暂时归档”。

### 方案 C：独立项目注册表，项目自身持有全部内容索引

**数据落点**

- `projects.v1.json` 保存项目对象、元件清单、场次/角色分组、排期和 owner 快照。
- `.muweave/` 只作为导入源，项目注册表成为 UI 的主要读取源。

**优点**

- 项目切换、归档、复制和自定义分组都容易实现。
- 列表读取可以不依赖当前 bundle 是否完整。
- 适合未来跨 workspace 的聚合项目。

**缺点**

- 注册表会变成第二数据库，必须维护与 owner 真源的一致性。
- 元件、状态、revision 和排期会出现重复副本，撤销、冲突和损坏恢复都更复杂。
- 初次同步、增量同步和删除重建都会增加用户可见的“同步失败”状态。

**迁移成本**

- 高。需要导入全部现有元素、排期和绑定，并制定冲突规则。
- 现有 `bundle.*` 与 `schedule.*` 契约都需要增加双向同步语义。

**两小时每周负担**

- 初期界面完整，但用户要理解“注册表同步”和“owner 同步”两套状态。
- 对单人低频使用者来说，维护成本最高。

## 推荐方案的边界

采用方案 B 的 `projectId` 作为事实连接键，吸收方案 C 的少量用户管理字段，但不保存内容索引。这形成一个窄的注册表边界。

- 注册表只保存项目身份和用户意图，包含 `id`、标题、项目状态、owner 安全引用、创建/更新时间、封面引用、归档标记和 workspace 引用。
- 元件列表、元件状态、场次、镜头、角色和素材类型全部实时读取 bundle 索引。分组和排序是查询视图，不写成项目副本。
- owner 绑定写入 bundle manifest 的既有 bindings，并由官方 owner CLI 或 `muweave-bundle` 完成。项目注册表只保存可安全展示的绑定引用和最后观察到的 revision。
- 同一个项目允许绑定多个 workspace，但一个 workspace 的 bundle `projectId` 只能绑定到一个注册表项目。冲突时停止写入并提示用户选择合并或解绑。
- 注册表缺失但 bundle 存在时，显示“待认领项目”，允许用户认领并补齐元数据。不能静默重写 bundle 的 `projectId`。

## 项目状态与元件状态

项目状态固定为五态：`preparing`（筹备）、`in_production`（制作中）、`ready_to_publish`（待发布）、`published`（已发布）、`archived`（归档）。

- 项目状态只由用户在项目层设置，`published` 和 `archived` 需要显式操作。
- 元件状态继续使用 owner/bundle 当前状态，例如草稿、待审阅、就绪、已完成和已过期。
- UI 先显示项目状态，再显示元件状态。项目状态旁可显示派生的“元件就绪摘要”，但摘要不能反写项目状态。
- 项目进入 `archived` 后默认隐藏在项目切换器和待排池，用户可打开“显示归档”恢复查看。归档不删除 owner 绑定、不删除 bundle、不清空排期。
- 项目切换只改变读取范围和当前上下文，不改变任何元件状态。

## 优先级

### P0：用户可以识别、创建和切换项目

1. **项目切换器**
   - 用户能看到项目标题、项目状态和最近更新时间，能在两个项目之间切换。
   - 当前项目上下文同时作用于 Workbench、Eikona、Script、Drama 和 Schedule 房间。
   - 归档项目默认隐藏，但可通过显示归档找到。
2. **新建项目与已有 workspace 绑定**
   - 用户能输入标题、选择现有 workspace、选择 owner 引用并完成一次显式同步。
   - 创建过程不会自动创建私有 owner 数据库，也不会把宿主路径写进项目记录。
   - 没有 owner marker 的来源显示为未初始化，用户可以稍后绑定。
3. **按项目过滤现有元件和排期**
   - 用户能在项目内看到元件总数、按 domain 的数量、owner readiness 和待审阅摘要。
   - 排期房间只显示当前项目可解析的 ref，跨项目切换不会混入条目。
4. **项目级状态操作**
   - 用户能设置筹备、制作中、待发布、已发布和归档，并能看到操作时间。
   - 项目状态与元件状态同时可见，不发生覆盖。

### P1：用户可以组织和复用项目

1. **派生分组与排序**
   - 用户能按场次、角色、状态和素材类型分组，也能按最近更新、状态优先、标题排序。
   - 分组切换不创建副本，不改变 bundle 或 owner 数据。
2. **项目绑定维护**
   - 用户能新增、替换或解除 Eikona/Auctra/Scaena 的安全引用，并看到绑定 revision 和同步时间。
   - 解绑前显示将失去哪些投影，不能删除 owner 原件。
3. **项目复制**
   - 用户能复制项目的标题前缀、状态初值和 workspace 选择记录，得到一个新的 `projectId` 草稿。
   - 复制只复制项目管理元数据，不物理复制 owner 目录、元件 payload 或排期。
4. **归档恢复与冲突提示**
   - 用户能恢复归档项目，能看到同一 `projectId` 被多个 workspace 声明时的明确冲突。

### P2：低频用户的维护和恢复体验

1. **待认领项目收敛**
   - 用户能一次确认旧 bundle 的标题、封面和状态，批量纳入项目切换器。
2. **同步与损坏诊断**
   - 用户能查看项目注册表、bundle 和 owner 的最后观察时间、revision 和可执行下一步。
   - 注册表损坏时保留原文件副本并以空注册表启动，用户可重新认领 bundle。
3. **项目摘要和低频复盘**
   - 用户能看到按项目计算的待审阅、过期、待排数量，但不虚构平台发布结果。

## 风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 把项目索引、元件状态或排期复制进 `.muweave/`，使其变成第二数据库 | `.muweave/` 只保留既有 manifest/index/elements/events。项目字段写入 `pluginDataDir/projects.v1.json`，元件和状态始终由 bundle/owner 读取。 |
| 直接读写 `.eikona/.auctra/.scaena` 私有目录 | 项目绑定只接受 owner CLI 返回的安全 ref，所有读取走官方 `--json`/handoff 或现有 bundle sync。 |
| 多 owner 目录被误当成一个项目 | 项目注册表保存 `workspaceId + owner ref` 的绑定集合。绑定前检查 marker、projectId 和 revision，冲突时阻止提交。 |
| 复制项目导致 owner 数据分叉 | “复制”只复制管理元数据并生成新 id，不复制目录、不复制 payload、不自动绑定旧 owner refs。 |
| 排期跨项目串线 | 读取时用当前项目的 bundle index 解析 ref，计划操作要求当前 `projectId` 上下文。旧 `schedule.v1` 条目无法解析时显示未归属并禁止移动。 |
| 项目状态被自动推导覆盖 | 派生摘要只作为辅助指标，项目状态只由 `project.update`/`project.archive` 显式修改。 |
| 注册表损坏或旧版本升级丢数据 | 使用版本化 schema、临时文件 + rename、`0600`、损坏文件隔离和逐版本迁移。 |
| 绝对路径、凭据或原始 provider payload 进入项目记录 | 项目对象只允许 opaque workspace/ref、digest、elementId 和标题等安全字段，RPC 入参继续经过明文凭据拦截。 |

## 不做什么

- **不把项目做成第二个 owner 数据库**。这会制造同步冲突，也违背 `.muweave/` 可重建约束。
- **不复制 `.eikona/.auctra/.scaena` 目录来实现项目复制**。复制目录无法证明 owner 真相一致，也会让低频用户承担不可见的迁移成本。
- **不在 P0 做自定义分组持久化**。按场次、角色、状态和素材类型已经可以从元件摘要派生，持久化自定义标签会引入另一套索引。
- **不把发布平台回执写成项目状态**。没有真实平台记录时只显示待发布和本地排期，不虚构已发布。
- **不在项目 RPC 中接受任意宿主路径或直接初始化 owner 目录**。目录注册和 owner 初始化继续遵循现有 workspace/CLI 合同，避免一次点击产生隐式数据。
- **不自建 DSH 窗口、可拖拽 dock 或跨房间 tab 系统**。项目管理使用官方全局页和现有房间入口，页内只使用固定区域和无分离能力的分段导航。
